# 红线与反例库（速查）

交付前与复盘时对照本文件逐项检查。

---

## 一、全局红线（11 条，任何步骤都不得违反）

| # | 红线 | 违反的典型表现 |
|---|---|---|
| 1 | **禁用形容词概率** | 输出"大概能成""大概率""比较有把握"而不给数字 |
| 2 | **基线先行不可颠倒** | 先凭感觉给概率，再拿基线去"修正" |
| 3 | **档案只追加不覆盖** | 回改历史概率值、改写更新日志旧行 |
| 4 | **AI 补充的假设必须打 `[AI补]`** | 把自己的假设混进用户条目里 |
| 5 | **样本 < 20 条不下校准结论** | 用 6 条预测就断言"我偏乐观" |
| 6 | **重要但不可预测 → 走情景规划** | 对云雾型问题硬给概率 |
| 7 | **未经外部基线校验的内部结果不得作为结论** | 把费米树的乘积直接当答案 |
| 8 | **个人决策场景不下"该不该做"的判决** | 输出"建议你不要创业" |
| 9 | **总概率的任何变动必须可追溯** | 未指明哪片叶子变化就改概率 |
| 10 | **颗粒度要求 ≠ 虚假精确** | 把 55% 写成 53.7% 以显得专业 |
| 11 | **档位命名必须对齐权威标准** | 自定义「重度/中度」档位，未查国标/WHO 分级，导致不同标准下同名档位指不同区间 |

## 二、分步红线速查

| 步骤 | 关键红线 |
|---|---|
| Step 0 | 出口未判定不得继续；多数问题应当死在这一步 |
| Step 1 | 不得透露基线；提问不得夹带数字；直觉估计锁定后全程封存 |
| Step 2 | B2 之前不得给叶子内容；不得用 Step 1 的数值做诱导；树不做计算 |
| Step 3 | **不得编造基线**；禁止 base-rate shopping；上位参考类不得在 Step 4 更换；必须与叶子基线同时锁定 |
| Step 4 | 禁止叶子乘积当总概率；差异点无证据即 0；**基线 ≥10% 累计 ≤ ±20 点，基线 <10% 改用倍数制（单因素 ≤×2、累计 ≤×3、下限 ≥×0.5）**；条件追问 ≤ 2 个节点 |
| Step 5–6 | 交付前过 10 项自检；编号永不复用；`.md` 与 `_ledger.json` 必须同步 |
| Step 7 | 归因必填；限幅不适用于逻辑必然；除逻辑必然外不得取 0/1；复核无变化也要留痕 |
| Step 8–9 | 判定标准登记即冻结；判定存疑单列；正式分用最终概率；ΔBS < 0 必须单独提示 |

## 三、各步骤反例汇总

### Step 2 · 费米分解

| 反例 | 病灶 |
|---|---|
| 三四个子事件各给概率直接相乘当总概率 | 忽略共因失效 + 虚假精确 |
| 用"互相独立"要求必要条件树 | MECE 措辞误用于 AND 树 |
| "用户会喜欢这个产品" | 不可检验叶子 |
| 拆到第 5 层还在往下拆 | 过度拆解 |
| AI 把自己的假设当成用户的假设 | 污染，必须打 `[AI补]` |

### Step 3 · 外部视角

| 反例 | 病灶 |
|---|---|
| 找不到数据就"估一个看起来合理的数"填进去 | **编造基线（最严重）** |
| 用"行业普遍认为约 30%"当基线 | 观点冒充数据 |
| 先看到基线觉得太低，改口换另一个参考类 | base-rate shopping |
| 把 L2 宽类基线当 L1 精确基线用 | 冒充精度 |
| 在 Step 3 就写"但我们团队更强，上调到 40%" | 内部视角污染外部视角 |
| 用"满意度 ≥ 4 分"的基线支撑"使用率 ≥ 60%" | 口径不一致 |
| 先给叶子基线，到 Step 4 才补上位参考类 | 违反同时锁定 |

### Step 4 · 概率锚定

| 反例 | 病灶 |
|---|---|
| 锚定基线后直接写"决定用 55%" | 差异点分析走过场，锚定过死 |
| 案例与参考类机制不同，仍按 ±5 点微调 | 结构差异未触发 |
| 因觉得 55% 太低而改用"成功率 80%"的参考类 | 顶层 base-rate shopping |
| 对全部 5 个叶子做条件追问 | 退化成全面条件概率法，用户负担不可持续 |
| 新信息来了直接改概率，不说明哪个叶子变了 | 更新不可追溯 |

### Step 5–6 · 输出与登记

| 反例 | 病灶 |
|---|---|
| 更新日志写"信息变化" | 触因不可追溯 |
| 发现旧概率写错，回改历史行 | 违反只追加 |
| 第二次预测直接续写旧档案 | 混淆两轮，Brier 无法算 |
| 只更新 md 忘了 json | 档案与总账脱节 |
| 交付物只有一段"大概率能成"的文字 | 违反颗粒度红线 |

### Step 7–9 · 更新与结算

| 反例 | 病灶 |
|---|---|
| 必要条件被证伪，仍按限幅慢慢减 | 把推理结论当调整 |
| 复核后无变化就不记录 | 失去心跳 |
| automation 自动判定并写结算 | 越权 |
| 结算时觉得判定标准写得不合理，改了再判 | 改考卷 |
| 结果不好 → 认定当初决策错了 | 混淆决策质量与结果质量 |
| 复盘写"我早就预感到会失败" | 后见之明叙事 |
| 只看一个总 Brier 分 | 分数相同病根不同，药方也不同 |
| 永久使用 50% 来"稳"分数 | 区分度归零 |

## 四、交付前总检查（10 项）

1. □ 概率是数字，不是形容词
2. □ 敏感区间已给
3. □ 上位参考类 + 来源 + 可信度等级齐备
4. □ 无基线叶子已显式标注
5. □ 头号瓶颈与条件追问结论已写
6. □ 风险项 + 预警信号（kill criteria）已写
7. □ 直觉对照表已完成
8. □ 场景对应的输出形态已选对
9. □ 更新可追溯字段已预留
10. □ 报告已完成双层结构（大白话 + 专业解读），且两层信息一致

## 五、冗余核查（防误报）

对「本技能是否存在冗余/可精简内容」的质疑，用以下实测结论回应，**不凭印象**：

| 检查项 | 工具 | 期望结果（每次改动后复跑复核）|
|---|---|---|
| 可精简文件（F_approx ≥ 0.7）| Distill 分析器 | **0 个**；7/7 全部「核心资产-保留」，F_approx ≤ 0.08 |
| 未被引用的 references | SkillOps 扫描器 | **0 个**（7/7 均被引用）|
| 断链 / 路径失效 | SkillOps 扫描器 | **0 处** |

**结论**：本技能无冗余文件。`references/` 各文件职责单一（准入 / 费米 / 外部视角 / 锚定 / 输出 / 更新 / 红线），互相引用清晰；再遇到"dim7b 冗余"类质疑，先复跑上述两个分析器，**有数据再改**。

## 六、三条支撑线自查

| 线 | 自查问题 |
|---|---|
| **数据卫生** | 每条数据的来源机构 / 年份 / 口径 / 可信度等级都标了吗？有没有用观点冒充数据？ |
